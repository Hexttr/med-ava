# Хранение данных: SQLite

## Текущая схема (актуально)

- **Организации и сотрудники** — SQLite (`data/eam.db`), фото в `data/uploads/organizations/<orgId>/`.
- **Галерея** — таблица `gallery_items` в той же БД, фото в `data/uploads/gallery/`.
- API: `GET/POST /api/organizations`, `GET/PATCH/DELETE /api/organizations/[id]`, `POST /api/organizations/[id]/employees`, `GET/POST /api/gallery`, `DELETE /api/gallery/[id]`, `GET /api/files/[...path]` (раздача файлов).

Папка `data/` в `.gitignore` — при первом запуске создаётся БД и каталоги.

---

## Когда имеет смысл переходить на БД

- Нужно хранить **много** организаций и сотрудников с фото без постоянной борьбы с квотой.
- Нужна **галерея между сессиями** (не терять портреты после закрытия браузера).
- Планируется **несколько пользователей/устройств** с общими данными.
- Развёртывание **локально в организации** — нормально добавить сервер/процесс с БД.

Для вашего сценария («устанавливается локально в разных организациях») база данных — разумный шаг.

---

## Варианты

### 1. SQLite + файлы на диске (оптимально для локальной установки)

- **Плюсы:** один файл БД, не нужен отдельный сервер БД, привычная модель «приложение + файл».
- **Минусы:** нужны API в Next.js, которые пишут в SQLite и в папку с файлами.

Схема:

- Таблицы: `organizations`, `employees` (id, org_id, name, photo_path), `gallery_items` (id, name, medical_path, corporate_path, organization_id, created_at).
- Фото хранить в папке на диске (например `data/uploads/` или `data/organizations/<id>/`), в БД — только путь или имя файла.

Стек: `better-sqlite3` или Prisma (driver `sqlite`) в API-роутах Next.js, запись файлов через `fs`/`fs.promises`.

### 2. IndexedDB (без бэкенда)

- **Плюсы:** не нужен сервер, квота обычно десятки/сотни MB, асинхронный API.
- **Минусы:** данные только в этом браузере на этом компьютере, галерея всё равно «внутри вкладки/профиля».

Имеет смысл, если хотите лишь увеличить лимит под организации/сотрудников и не готовы поднимать БД.

### 3. PostgreSQL / MySQL + файлы или S3-совместимое хранилище

- Нужно только если планируется общий сервер, несколько инстансов приложения или облачное развёртывание.
- Для локальной установки в каждой организации обычно избыточно.

---

## Рекомендация

Для приложения, которое **ставится локально в организациях**:

- Переход на **SQLite + хранение фото в файлах** даёт:
  - стабильное хранение без квот;
  - галерею, сохраняющуюся между сессиями;
  - возможность бэкапов (скопировать папку с приложением и файлом БД + каталог с фото).

Минимальный объём работ:

1. Добавить зависимость (например `better-sqlite3` или Prisma с SQLite).
2. Создать файл БД (например `data/eam.db`) и миграции/схему для организаций, сотрудников и галереи.
3. API: `GET/POST /api/organizations`, `GET/POST/PATCH/DELETE /api/organizations/[id]`, сохранение фото в `data/uploads/...` и запись путей в БД.
4. API галереи: `GET/POST /api/gallery`, отдача картинок по путям (или через роут вида `/api/files/[...path]`).
5. На фронте заменить чтение/запись в localStorage/sessionStorage на вызовы этих API.

Если нужно, могу расписать конкретные шаги и пример кода под выбранный вариант (SQLite + файлы или только IndexedDB).
